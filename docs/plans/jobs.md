# Store jobs on the server

Everything that writes the store moves from GitHub Actions to a job queue on the Stillwell server, one source at a time, so that one process orders every writer and the work a merged change needs runs on its own. [realtime.md](realtime.md) keeps the poller and the plan for ClickHouse; this is the queue that plan's step 2 assumed, built first without ClickHouse: jobs run `scripts/ingest.ts` against R2 as the workflows do now.

## Goals

- **One writer per file.** Every job that writes a source's files runs in that source's lane, one at a time, and nothing outside the queue writes them. Actions' `store-<source>` concurrency groups go, with the cancellations of waiting runs they bring.
- **Migrations run themselves.** A change that needs store work after it merges carries it as a migration in `src/migrations/`, which the server runs once, step by step, instead of a checklist someone dispatches by hand.
- **Nothing collides during the move.** A source's writers are all in Actions or all on the server, never some of each.

## The queue

`stillwell-jobs` (`server/jobs.ts`) is a service on the box, running as root, with a SQLite database in Node's built-in `node:sqlite`, `/var/lib/stillwell-jobs/jobs.db`, in a directory only root writes. The `stillwell-jobs` command on the box (`server/jobs-cli.ts`) adds and cancels jobs through the same database.

- **A job** is a command: the arguments of one `scripts/ingest.ts` run, or one migration's check. It has a lane, a timeout and a state: `queued`, `running`, `cancelling`, `succeeded`, `failed` or `cancelled`. An optional key, such as a schedule's `compact:ea:2026-11-16`, keeps the same job from being queued twice. Its arguments are parsed with `scripts/ingest.ts`'s own options (`src/ingest-options.ts`) and checked for the words each command takes before it's queued. `drop`, `withhold` and `misplaced` aren't jobs yet, since they delete with the `aws` CLI, which the box doesn't have.
- **Lanes** are Actions' concurrency groups, chosen the same way (`laneOf`): `store-<source>` for a command on one source, `store` for `publish` and the rest, `links` and `matches`. One job runs per lane, and at most three at once across lanes, of which at most two may run over an hour, so long jobs leave a slot for the hourly and nightly ones. A lane's short jobs start before its long ones, each in the order queued, so an hourly run waits behind at most the one long job running. A check, which only reads, takes no lane, and waits, as store jobs do, for the store's credentials.
- **Ownership.** [`src/sources/server.json`](../../src/sources/server.json) maps each source moving to or on the server to its phase, read as `PHASES`. Actions never writes a source in any phase: the scheduled workflows leave it out, and every workflow job that writes one source reads `main`'s map before it writes ([`scripts/server-owns.sh`](../../scripts/server-owns.sh)), so a run queued, or re-run, from a commit before the source moved fails rather than write it, as does one when `main`'s map can't be read. The server writes only sources in the `server` phase, and runs checks, which only read. The `store`, `links` and `matches` lanes stay in Actions until every source has moved, since `publish`, `links` and `matches` read every source and write files of their own.
- **Schedules.** For each source in the `server` phase, the service queues the runs Actions makes for the others, at the same times (`due` in [`src/jobs/schedule.ts`](../../src/jobs/schedule.ts)): `recent --hours 12` from 12 minutes past each hour for an hourly source, `compact --days 6` from 00:40 UTC, and on the 2nd and the 9th the steps of Monthly's list job and refetch, which both run from [`scripts/monthly.sh`](../../scripts/monthly.sh). Each run is keyed by its period, so it's queued once, and one isn't queued while another of the same kind for the source still waits, so a lane held by a long backfill doesn't pile them up. A monthly run is queued within three days of its time, so a source that moves later in the month waits for the next month's, and one that moves within those days can run twice that month. Compaction runs at half Actions' concurrency, since a job's memory is a fifth of the box rather than a runner's 16 GB. When a source on the server reports a station in another datum, the service reads it from the poller's `polls` table and queues the source's list refresh, once a day. When a source leaves the `server` phase, the service cancels its queued jobs, so none starts if it comes back.
- **Handover.** A source moves to the server in one pull request, which adds it to `server.json` as `server`. Actions stops writing it at once, and the server starts writing it once no Actions run may still do so: before starting any store job, the service asks GitHub, every five minutes, which sources an Actions run queued or running may still write, and which `main`'s `server.json` puts in the `server` phase. It starts a source's jobs only when `main` has it in that phase too, so a box deployed from a branch, or left behind by a failed deploy, writes only what `main` gives it, and none while an Actions run may write the source, nor any while it can't tell, such as without `GITHUB_TOKEN` in `/etc/stillwell.env` or while a scheduled run's matrix hasn't expanded. A re-run of a workflow run counts too, even one from before the guard existed, which GitHub re-runs with its own commit's workflow file and so would write the source unguarded: the service starts nothing for the source while it runs, asking GitHub again before it starts a store job unless its answer is under 15 seconds old, and takes an Ingest run titled only `Ingest`, from before its runs named their arguments, as writing every source; a job of the source's already running when someone starts one still overlaps it, so nobody re-runs a run created before the guard reached `main`, on 2026-11-16, for a source on the server. Meanwhile its scheduled runs wait in its lane, and the first hourly `recent` catches up 12 hours, so a source moves when no long Actions campaign is writing it. On the 2nd, Monthly's `matches`, `links` and `publish` no longer wait for a server source's list refresh, which runs on the server at the same time, so they can read its files before its requalify ends; `publish` catches up the next night, and `matches` and `links` the next month. A source moves back in two, never by reverting the change that moved it, which would hand it to Actions while a job of its may still be running: `returning` stops the server queuing and starting its jobs, and once `stillwell-jobs list` shows none running, the source leaves the file and Actions writes it again, since Actions can't see the server's jobs. Each move ends with closing, by hand, any open "Ingest hourly is failing" or "Compact daily is failing" issue for the source, which `scripts/alert.sh` closes only when the source's job succeeds in Actions again. Jobs run at most 10 hours, under the 12 hours a source's next hourly `recent` catches up after waiting behind one. On the server, Monthly's analysis and requalify run as many stations at once as a job's memory holds, rather than Actions' 8.
- **Running.** Each job runs as a transient systemd unit, `stillwell-job-<id>`, as the `stillwell` user, capped at a fifth of the box's memory, with a V8 heap at 60% of that, and at a lower CPU weight than the poller, with its timeout as the unit's `RuntimeMaxSec`, in `/var/lib/stillwell-jobs/runs/<id>`, which holds its response cache and is deleted when it ends. It reads `/etc/stillwell.env` as the poller does; its own variables, `STILLWELL_WRITE_STORE` as its `STILLWELL_STORE` among them, go on its command through `env`, since systemd lets a unit's environment file override them, and it runs Node through the `/opt/node` link, which a deploy that upgrades Node moves rather than removes. A restart of `stillwell-jobs` leaves running jobs alone and reads their units' results when it starts again, and a unit it can't read is read again on the next pass, never taken as ended. Its log is the unit's journal: `journalctl -u stillwell-job-<id>`. Only the service stops a job: a cancel marks a running job `cancelling`, which keeps its lane until the service has stopped it. A job's working directory is its own, so a file it names, such as `--first`, takes an absolute path, such as `/opt/stillwell/docs/ticon-inventory.csv`.
- **Code.** A job runs the release it started with. Deploys install each release in a directory of its own under `/opt/stillwell-releases`, point `/opt/stillwell` at the newest, restart `stillwell-jobs` on it, and delete an older release only once no process runs from it, so no deploy removes code a running job uses.
- **Failures.** A failed job stays failed; nothing retries it on its own. The service writes the count of failed jobs and the queue's depth to its metrics file, and Grafana alerts on a new failure.

## Migrations

A migration is a file in `src/migrations/` named `YYYYMMDD-what-it-does.ts`, exporting its steps: `ingest` arguments, or a `check` that reads the store and throws when it's wrong. The service runs migrations one step at a time across all of them, in file-name order: it queues a step as a job, waits for it, and queues the next, recording the step's job in the same transaction that queues it.

- A step whose lane the server doesn't own yet would wait there, holding every migration after it, so `npm test` refuses a migration with such a step, and with a check but no step the server runs, since that check would read the store before the work it checks. Until a change's sources have moved, its store work stays in the pull request's `## After merge`.
- A failed step stops every migration until `stillwell-jobs retry <id>` runs it again, or `stillwell-jobs skip <id>` marks the migration done without its remaining steps, a decision to make once they can't or needn't run.
- A new migration that sorts before one already recorded isn't run or recorded, and holds every migration after it until it's renamed to sort after.
- The service reads each migration's steps when it starts, which every deploy of a new release makes it do, so a deploy that edits one under way changes what runs next, and its record keeps only a step's number: edit one only before it starts.

The database records each migration's progress. A box with no database, a new one, runs no migration until a maintainer runs `stillwell-jobs baseline <id>` with the last one already done, which marks it and every earlier one done, so a replacement box never runs every migration again, and one merged later under an earlier name is caught as sorting before them. The first deploy of the queue records none and starts the record, since `src/migrations/` is empty then.

## Starting jobs

The `stillwell-jobs` command runs on the box over ssh: `enqueue [--timeout minutes] <ingest args>`, `list`, `cancel <id>`, `migrations`, `retry <migration>`, `skip <migration>`, `baseline <migration|none>` and `selftest [fail]`. Store work a merged change needs belongs in a migration, so it's reviewed with the change; `enqueue` is for one-off work, such as a backfill campaign.

## Order of work

1. **The queue, its schedules and the handover**, with `server.json` empty, so nothing changes in the store.
2. **The first source.** Before it moves, the box is at least 16 GB, `/etc/stillwell.env` holds `STILLWELL_WRITE_STORE` and the R2 credentials to write it, and the peak memory of the source's largest commands, such as `requalify … all` and `analyze --requalify` at their concurrency, is measured under the per-job cap. Then one quiet source moves. Compact daily's and Monthly's `publish` pick up what the server wrote at their next run, and a datum change it opens is accepted by queuing `stations <source> --no-publish --accept-epochs` by hand.
3. **Every source**, a few at a time, each after its running Actions campaigns finish or are queued again on the server, and with the PM told before each. SFWMD refuses the box's address, so it stays in Actions, which keep writing its `recent/` for the poller, until something that can reach it does.
4. **The cross-source lanes.** `publish`, `links`, `matches` and the cross-station report move, the `store-<source>` groups and the scheduled ingest workflows retire, and the `aws` CLI or a replacement lets `drop` and `withhold` run as jobs.

A source that moves back has done migrations with steps the server can't run, which `npm test` refuses, so the change that takes it out of `server.json` deletes them too: a done migration is never needed again.
