# Operations

## Ingest on R2

The Ingest workflow runs [`scripts/ingest.ts`](../../scripts/ingest.ts) against the public `water-levels` bucket. Only maintainers can start it, and its credentials live in the `lake` environment, which only runs on `main`. Two workflows run on a schedule from the same environment, each source a job of its own: Compact daily runs `compact --days 6` at 00:40 UTC, so late values, revised flags and a missed night still reach the year files, then runs `publish` so `stations.parquet` carries the bounds it wrote. Both can also be started by hand. Monthly refreshes each source's list on the 2nd at 01:25 UTC, each in a job of its own in the source's `store-<source>` group, then publishes `stations.parquet` in the `store` group. Each list job then runs the source's own list backfills, if it has any (see [Adding a source](sources.md#adding-a-source)). On the 9th at 03:35 UTC it refetches values the source may have finalized since, for every source whose metadata sets `finalizes`, with the backfills its `schedule` gives (see [Adding a source](sources.md#adding-a-source)). Both can be started by hand, for some sources, with `refetch` checked for the second, which fails when none of the sources named finalizes its values; the Ingest workflow refuses `stations`, so lists are refreshed only here, with `accept_epochs` checked to pass `--accept-epochs`. The poller starts a Monthly refresh of one source, at most once a day counting any dispatched refresh that includes the source (a scheduled Monthly, normally a backup that plans nothing, doesn't count), when it fails a station with `DatumChanged`, which an adapter throws when it sees a station's datum change between refreshes; a change no adapter sees waits for the 2nd. Monthly also keeps the schedules alive: GitHub disables a public repo's scheduled workflows after 60 days without a commit, and enabling each one through the API every month restarts that count; one a maintainer turned off stays off. If GitHub ever disables them anyway, enable each one again from its page in Actions, Monthly first. Every job that writes one source's files, a manual `backfill`, `compact`, `withhold` or `drop` included, runs in that source's `store-<source>` concurrency group, so no two rewrite one file at once. Station lists are refreshed only by Monthly, so a refresh never runs beside another refresh of the same list or the source's other jobs, and `stations.parquet` is published only in the `store` group, by Monthly's or Compact daily's `publish` job or an Ingest `publish`. Each checks out `main` as it is when the job starts, so one that waited doesn't publish from a build older than a source's registration, which would drop that source's stations. No source's job takes that group, and a publish runs in about a minute, so it never holds up a backfill; Compact daily's waits for every source's compaction, though, and so for any backfill holding one up. Ingest's other commands without a source run in the `store` group too. Every group that touches the store sets `queue: max`, so runs wait in the order they arrive, up to 100, and a run waiting is never cancelled by the next: a compaction waits behind a long backfill, and a manual run behind the source's scheduled job.

GitHub's `schedule` trigger runs workflows hours late or not at all, so a Cloudflare Worker, [workers/cron](../../workers/cron/README.md), starts Compact daily and Monthly at those times, Canary at 07:00 UTC on Mondays, and Migrations at 20 past each hour, through the `workflow_dispatch` API. Each workflow keeps its `schedule`, five minutes later, as a backup. A scheduled run first looks for a dispatched run that already started on `main` (in the last 23 hours for Compact daily, the last day for a Monthly run of the same title, Monthly or Refetch for every source, and the last day for Canary; Migrations' backup at 25 past takes the next step, if any, so it doesn't look) and runs nothing if it finds one, since a second run would queue in each source's group and run each source's jobs again. Bucket check stays on GitHub's schedule alone.

When a source's job fails in two Compact daily runs on `main` in a row, dispatched or scheduled, the workflow's `alert` job ([`scripts/alert.sh`](../../scripts/alert.sh)) opens an issue titled "Compact daily is failing for <source>", and closes it when that job next succeeds. Compact daily's `publish` counts as a source of its own, "Compact daily is failing for publish". It opens one issue per source at a time. A job cancelled or skipped before its first step, such as one cancelled while it waited on its group, doesn't count either way; any other that didn't succeed, a timeout or a cancelled job that had started included, is a failure. It runs only on a run's first attempt, since a re-run would judge a source by an older result than its latest, and not on a backup that found a dispatched run and skipped.

## Live polling

The poller runs in the live Worker's container ([workers/live](../../workers/live/README.md), [Running the poller](poller.md)), and the daily files it writes, `recent/<source>/<YYYY-MM-DD>.parquet`, are the only live files on R2: today's rewritten at 5 past each hour, and the 7 days up to today after midnight UTC and when the poller starts. Compact daily folds them into the year files. The Worker's cron asks the container's `/health` every minute, which starts it if it isn't running. At 30 past each hour it opens an issue titled "Live polling is failing for <source>" for each source with no clean pass in 2 hours, and closes it after a clean one. The container's recent output is the poller's `GET /log`, which the Worker serves to holders of `STORE_TOKEN` and logs every 10 minutes. At 03:45 UTC the Worker deletes station-days older than 8 days from D1 and passes older than 30.

CI deploys `workers/live`, `workers/api` and `workers/cron` on each push to `main`, once the `cloudflare` environment holds the secret `CLOUDFLARE_API_TOKEN` and the repository variable `CLOUDFLARE_ACCOUNT_ID` is set.

## Migrations

A change that needs work done to the store after it merges, such as a requalify after a QC or errata change or a refetch after an adapter fix, carries that work as a migration: a file in [`src/migrations/`](../../src/migrations/README.md) listing its steps, each `ingest` arguments or a `check` that reads back what the steps before it wrote and throws when the store is wrong, as [Rigor](../../CONTRIBUTING.md#rigor) asks for after merge. The [Migrations workflow](../../.github/workflows/migrations.yml) runs them once, one step at a time across all of them, in file-name order. It starts on each push to `main`, from the cron Worker at 20 past each hour, and from a GitHub schedule at 25 past, and each run takes one step and starts the next run when it succeeds. Each step runs in its source's `store-<source>` concurrency group, so it never rewrites a file another job is writing, with a timeout of up to 360 minutes. A step waits in its group's queue behind whatever runs there, without cancelling anything waiting; one cancelled before it starts, as when the queue is full, isn't recorded, and the next run takes it again.

The workflow records progress in `migrations.json` in the store. A store with no record runs no migration until a maintainer begins one by dispatching the workflow with `baseline` and the last migration already done, or `none`, which marks it and every earlier one done. `node scripts/migrations.ts list` prints the record.

- `drop`, `withhold` and `misplaced` are steps like any other. A step passes no `--accept-*` flag or `--dry-run`, since those accept whatever the source reports when the step runs, long after the review. A requalify with a `--budget`, as `analyze --requalify` always has, takes one of at least its timeout, so it never stops early and succeeds. `npm test` also parses each step as `scripts/ingest.ts` would and checks the words its command takes.
- A failed step opens an issue titled "Migration <id> failed" and stops every migration after it. Dispatch the workflow with `retry` and the migration's name to run the step again, or with `skip` to mark the migration done without its remaining steps.
- A migration that sorts before one already recorded isn't run, so rename it to sort after. Edit a migration only before it starts: one that has run doesn't run again, so add a new one instead.

## Costs

Per month, from Cloudflare's published prices in November 2026. A container is billed for its memory and disk while it runs, and for CPU only while in use.

| D1                | up to 58 million rows written, against 50 million included, a few hundred MB stored   |       $0–8 |
| The levels API    | Workers requests and CPU, inside the plan's 10 million requests and 30 million CPU ms |         $0 |

The poller is most of it, since a container's memory is billed all month: one that ran a pass at a time would fit `basic`, 1 GiB and a quarter of a vCPU, for about $20.

## Canary

The Canary workflow runs [`scripts/canary.ts`](../../scripts/canary.ts) each Monday: the probes in each `src/sources/<source>/canary.ts`, one small request per adapter, through the adapter's own code and pacing, for a few days at a gauge that has run for years. It fails when a probe returns no values or throws, or when a response's shape (each JSON path and its types, or for a text format the code that starts each line) has lost a path or gained a type since the shape recorded in `src/sources/<source>/canary.json`. A field the source adds doesn't fail it, and neither does a null where the recording had a value or an object, or a value where it had only null. A source with no recording yet prints its shape and has only to return values. A probe whose request paths change or whose responses have no shape sets `recorded: false`, with a comment saying why, and has only to return values. A probe that needs a key lists it in `env` and is skipped without it; its secret is passed in [`canary.yml`](../../.github/workflows/canary.yml), since the canary doesn't run in the `lake` environment. Once the adapter handles a change, check the new shape and record it:

```bash
node scripts/canary.ts <source> --record
```
