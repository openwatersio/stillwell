# Operations

## Ingest on R2

The Ingest workflow runs [`scripts/ingest.ts`](../../scripts/ingest.ts) against the public `water-levels` bucket. Only maintainers can start it, and its credentials live in the `lake` environment, which only runs on `main`. Two workflows run on a schedule from the same environment, each source a job of its own: Compact daily runs `compact --days 6` at 00:40 UTC, so late values, revised flags and a missed night still reach the year files, then runs `publish` so `stations.parquet` carries the bounds it wrote. Both can also be started by hand. Monthly refreshes each source's list on the 2nd at 01:25 UTC, each in a job of its own in the source's `store-<source>` group, then publishes `stations.parquet` in the `store` group. Each list job then runs the source's own list backfills, if it has any (see [Adding a source](sources.md#adding-a-source)). On the 9th at 03:35 UTC it refetches values the source may have finalized since, for every source whose metadata sets `finalizes`, with the backfills its `schedule` gives (see [Adding a source](sources.md#adding-a-source)). Both can be started by hand, for some sources, with `refetch` checked for the second, which fails when none of the sources named finalizes its values; the Ingest workflow refuses `stations`, so lists are refreshed only here, with `accept_epochs` checked to pass `--accept-epochs`. The poller starts a Monthly refresh of one source, at most once a day counting any dispatched refresh that includes the source (a scheduled Monthly, normally a backup that plans nothing, doesn't count), when it fails a station with `DatumChanged`, which an adapter throws when it sees a station's datum change between refreshes; a change no adapter sees waits for the 2nd. Monthly also keeps the schedules alive: GitHub disables a public repo's scheduled workflows after 60 days without a commit, and enabling each one through the API every month restarts that count; one a maintainer turned off stays off. If GitHub ever disables them anyway, enable each one again from its page in Actions, Monthly first. Every job that writes one source's files, a manual `backfill`, `compact`, `withhold` or `drop` included, runs in that source's `store-<source>` concurrency group, so no two rewrite one file at once. Station lists are refreshed only by Monthly, so a refresh never runs beside another refresh of the same list or the source's other jobs, and `stations.parquet` is published only in the `store` group, by Monthly's or Compact daily's `publish` job or an Ingest `publish`. Each checks out `main` as it is when the job starts, so one that waited doesn't publish from a build older than a source's registration, which would drop that source's stations. No source's job takes that group, and a publish runs in about a minute, so it never holds up a backfill; Compact daily's waits for every source's compaction, though, and so for any backfill holding one up. Ingest's other commands without a source run in the `store` group too. A run waiting in a group is cancelled when the next one arrives, so while a long backfill holds a source, its compaction skips until it's done, and the next one's 6 days catch up. That goes for a manual run too: one started while the source's scheduled job is running can be cancelled by the next run, so start it when the group is free, and check that it started rather than show as cancelled.

A source in [`src/sources/server.json`](../../src/sources/server.json) is the exception to all of this: the workflows leave it alone, and its nightly and monthly jobs, list refreshes included, run on the server's job queue instead, one at a time in the source's lane (see [Migrations](#migrations)).

GitHub's `schedule` trigger runs workflows hours late or not at all, so a Cloudflare Worker, [workers/cron](../../workers/cron/README.md), starts Compact daily and Monthly at those times, and Canary at 07:00 UTC on Mondays, through the `workflow_dispatch` API. Each workflow keeps its `schedule`, five minutes later, as a backup. A scheduled run first looks for a dispatched run that already started on `main` (in the last 23 hours for Compact daily, the last day for a Monthly run of the same title, Monthly or Refetch for every source, and the last day for Canary) and runs nothing if it finds one, since a second run would wait in each source's group and cancel any job already waiting there. Bucket check stays on GitHub's schedule alone.

When a source's job fails in two Compact daily runs on `main` in a row, dispatched or scheduled, the workflow's `alert` job ([`scripts/alert.sh`](../../scripts/alert.sh)) opens an issue titled "Compact daily is failing for <source>", and closes it when that job next succeeds. Compact daily's `publish` counts as a source of its own, "Compact daily is failing for publish". It opens one issue per source at a time. A job cancelled or skipped before its first step, such as one cancelled while it waited on its group, doesn't count either way; any other that didn't succeed, a timeout or a cancelled job that had started included, is a failure. It runs only on a run's first attempt, since a re-run would judge a source by an older result than its latest, and not on a backup that found a dispatched run and skipped.

## Migrations

Store writes are moving from Actions to a job queue on the Stillwell server, one source at a time ([docs/plans/jobs.md](../plans/jobs.md)). [`src/sources/server.json`](../../src/sources/server.json) maps each source on the server to its phase, `server` or `returning`: the scheduled workflows leave them out, every workflow job that writes one refuses it by `main`'s map, and only those in the `server` phase are written, by the server, which runs their nightly and monthly jobs at Actions' times. Move a source with one pull request adding it as `server`, which the server writes once no Actions run still does; back with two, `returning` and then, once `stillwell-jobs list` shows none of its jobs running, removing it. Monthly's per-source steps are [`scripts/monthly.sh`](../../scripts/monthly.sh), which both run. Queue one on the box with `stillwell-jobs enqueue [--timeout minutes] <ingest args>`, and follow it with `journalctl -fu stillwell-job-<id>`.

A change that needs work done to the store after it merges, such as a requalify after a QC or errata change or a refetch after an adapter fix, carries that work as a migration: a file in [`src/migrations/`](../../src/migrations/README.md) listing its steps, each `ingest` arguments or a `check` that reads back what the steps before it wrote and throws when the store is wrong, as [Rigor](../../CONTRIBUTING.md#rigor) asks for after merge. The server runs migrations once, one step at a time across all of them, in file-name order, each step as a job.

- `npm test` refuses a migration with a step the server can't run yet, since it would hold every migration after it, and one with a check but no step the server runs, since the check would read the store before the work it checks. So until a change's sources have moved, its store work stays in the pull request's `## After merge`, as does a `drop` or `withhold`, which the server can't run yet.
- A step passes no `--accept-*` flag or `--dry-run`, since those accept whatever the source reports when the step runs, long after the review. A requalify with a `--budget`, as `analyze --requalify` always has, takes one of at least its timeout, so it never stops early and succeeds. `npm test` also parses each step as `scripts/ingest.ts` would and checks the words its command takes.
- A failed step stops every migration until `stillwell-jobs retry <migration>` runs it again, or `stillwell-jobs skip <migration>` marks it done without its remaining steps.
- A migration that sorts before one already recorded isn't run, so rename it to sort after. Edit a migration only before it starts: one that has run doesn't run again, so add a new one instead.

## Canary

The Canary workflow runs [`scripts/canary.ts`](../../scripts/canary.ts) each Monday: the probes in each `src/sources/<source>/canary.ts`, one small request per adapter, through the adapter's own code and pacing, for a few days at a gauge that has run for years. It fails when a probe returns no values or throws, or when a response's shape (each JSON path and its types, or for a text format the code that starts each line) has lost a path or gained a type since the shape recorded in `src/sources/<source>/canary.json`. A field the source adds doesn't fail it, and neither does a null where the recording had a value or an object, or a value where it had only null. A source with no recording yet prints its shape and has only to return values. A probe whose request paths change or whose responses have no shape sets `recorded: false`, with a comment saying why, and has only to return values. A probe that needs a key lists it in `env` and is skipped without it; its secret is passed in [`canary.yml`](../../.github/workflows/canary.yml), since the canary doesn't run in the `lake` environment. Once the adapter handles a change, check the new shape and record it:

```bash
node scripts/canary.ts <source> --record
```
