# Kartverket (`kartverket`)

Observed water levels from the permanent tide gauges of Kartverket, the Norwegian Mapping Authority's Hydrographic Service, from its [tide API](https://vannstand.kartverket.no/tideapi_en.html) (`tideapi.php`), documented in its [communication protocol](https://vannstand.kartverket.no/API%20for%20water%20level%20and%20tides%20-%20communication%20protocol_revJune2025.pdf) (revised June 2025). 32 gauges on the Norwegian coast and one on Svalbard, at 10-minute intervals, from the 1980s.

- **License:** [CC BY 4.0](https://creativecommons.org/licenses/by/4.0/). The [terms](https://kartverket.no/en/api-and-data/tides-and-water-level-data) say "the Norwegian Mapping Authority, Hydrographic Service must be credited, since we are licensee of the data", so the attribution is "Norwegian Mapping Authority, Hydrographic Service". The license allows republishing and commercial use, so every station goes to the public lake, tagged for commercial use. The API needs no registration.
- **Stations:** every station `stationlist` lists with type `PERM`, as `kartverket/<code>` with Kartverket's three-letter code in capitals (`kartverket/BGO` for Bergen). Each refresh also asks `obstime` for each station's first observation, kept as `record_start` in the lake's list so a backfill doesn't ask for years before it, and `stationlevels` for its datum offsets: 67 requests, about a minute. Ny-Ålesund is `SJ` (Svalbard); the rest are `NO`. Every station is `coastal` and live. `source_url` opens Se havnivå at the gauge's position. An empty list fails the refresh.
- **Levels:** `stationdata` with `datatype=obs` and `interval=10`, in centimeters to a tenth, stored as meters. The API calls these values "filtered 10 minute data". Bergen's 1990 values change by different amounts within each hour, so they aren't hourly readings interpolated linearly, though the API doesn't say how they were sampled.
- **Flags:** the API marks every observation `obs` and carries no quality flag, though Kartverket says it revises recent values. Values measured within the last 365 days are `preliminary` and older ones `good`; the year is our choice, not Kartverket's. Any other flag is `suspect`.
- **Times:** requests ask for `tzone=0` and `dst=0`, so every timestamp comes as UTC (`+00:00`) and is read as the instant it names. Without `tzone`, the API answers in Norwegian standard time (UTC+1) all year. A March 2025 month at Bergen comes back as 4,465 values, every 10 minutes through the change to summer time, with none missing or doubled. `fromtime` and `totime` are both inclusive and given to the minute, so the adapter drops the value at the range's end.
- **Clock check:** on 2015, against UHSLC's records of Vardø, Tregde and Ny-Ålesund and CMEMS's of Bergen, every series fits best within 10 minutes of zero, and K1's phase puts Vardø, Ny-Ålesund and Bergen within 7 minutes. Tregde's tide is a few centimeters, so weather dominates its series (r 0.59) and its K1 lag of 128 minutes says little; it is still under the check's 3-hour limit.
- **Datum:** chart datum (`CD`), the API's default and the only reference every station has; Ny-Ålesund has no NN2000. The API serves a station's whole record against its current chart datum. `stationlevels` gives mean sea level (1996–2014) and NN2000 above chart datum, kept in `datums` (Bergen: `MSL` −0.952 m, `NN2000` −1.022 m). A response in any other reference is refused. Chart datum is tidal, so Kartverket can redefine it, and the API would then serve the whole record against the new one while the lake's years stay on the old. `seriesChanged` compares chart datum's height in NN2000 with the lake's list, and a move of more than a centimeter opens or holds a datum epoch for a person to decide ([docs/stations.md](../../../docs/stations.md)); Ny-Ålesund has no NN2000, so a change there goes unseen. Between refreshes, a backfill asks each station's offsets once and refuses a station whose chart datum has moved, so Monthly's refetch on the 9th can't write the new datum's values into the old epoch's files before the refresh on the 2nd opens the new one. A refresh that can't read a gauge's offsets keeps the ones the lake's list has, so the next refresh can still compare. Since the API serves the whole record against today's chart datum, the source declares `archive: "current"` and lists no `reference`. The list names chart datum for every station, so a response in another reference fails each request until a person decides what to do; the refresh can't open an epoch for it.
- **Limits:** the API documents capacity for about 20 requests a second, shared by all users, and asks not to be polled hard. Requests start at least a second apart. A year in one request works (a year of hourly values at Vardø took 5 seconds). A month of 10-minute values at Bergen is 320 KB and took 3.4 seconds, so a station-year is about 3.8 MB and roughly 30 to 40 seconds. Responses aren't compressed. A bad request answers 200 with an `<error>` element, which fails; a range with no data answers an empty `<location>`.
- **History:** from 1986 to 1992 at the long-running gauges, later at newer ones (Oslo from 2006, Mausund from 2010, several from 2021 to 2026). Older records, back to 1914 at Oslo and 1915 at Bergen, aren't in this API; Kartverket points to the Copernicus Marine Service for them. `stattime` gives the years with monthly means, which reach further back than the observations.
- **Freshness:** the station list, `obstime` and `stationlevels` are never cached. A year's levels are cached only when the whole range is more than 365 days old and the response runs to its last 10 minutes. Values arrive 10 to 20 minutes after they're measured, so the gauges suit Ingest hourly.

## Backfill

The Monthly workflow refreshes Kartverket's list on the 2nd with every other source's; dispatch it with `sources: kartverket` once as soon as the adapter is on `main`, since Ingest hourly and Compact daily fail for Kartverket until its list is in the lake, and the backfill needs each station's `record_start` from it. A gauge whose first observation or datum offsets can't be read is listed without them, with a warning. Then, through the Ingest workflow:

```bash
node scripts/ingest.ts backfill kartverket all 1986 2026 --skip-written --first docs/ticon-replacement.csv
node scripts/ingest.ts backfill kartverket all 2026 2027
```

That's about 880 station-years before 2026, one request each, about 3.3 GB. At 30 to 40 seconds a request and the default 4 stations at once, it should take 2 to 3 hours, so one 6-hour Ingest run, or two if the server slows under parallel requests. The current year is fetched in full on every run, so it's backfilled on its own. From then on, Ingest hourly keeps the gauges current, and Monthly's refetch on the 9th (`backfill kartverket preliminary`) fetches each station again from its earliest preliminary value, so values pick up Kartverket's revisions until they turn a year old.
