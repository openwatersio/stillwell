# LINZ (`linz`)

1-minute sea levels from the tsunami gauge network of Toitū Te Whenua Land Information New Zealand (LINZ): 19 gauges around New Zealand, the Chatham Islands and Raoul Island, from 2007, served by an open download API at `https://sealevel-data.linz.govt.nz/` behind the [sea level data downloads](https://www.linz.govt.nz/products-services/data/types-linz-data/sea-level-data/sea-level-data-downloads) page. The network was set up between 2007 and 2010 to improve New Zealand's response to tsunamis.

- **License:** the download page says "This work is licensed under a Creative Commons Attribution 3.0 New Zealand License" and asks users to "attribute the work to Land Information New Zealand". CC BY has no non-commercial condition, so every station goes to the public store, tagged for commercial use, with the attribution "Land Information New Zealand" and a link to the [license](https://creativecommons.org/licenses/by/3.0/nz/). The statement is on the page, not in each file or README, and covers all the gauges listed there. The API needs no key.
- **Contact for errors:** customersupport@linz.govt.nz or the [contact page](https://www.linz.govt.nz/contact-us). The Cape Roberts README names the same mailbox for data before 2007.
- **Stations:** `GET /api/listGauges` gives 21 codes, and `GET /api/getGaugeData/<CODE>` gives each one's README (`description`) and its list of year and sensor datasets. A gauge is listed as `linz/<CODE>`, with LINZ's four-letter code, when it has sensor 40 files. Its name and position come from the README, whose position lines vary (`44° 01" 26"S`, `170° 37' 46E`, no seconds). `kind` is `coastal`, `country_code` `NZ`, `interval_s` 60. A gauge whose README can't be read keeps its entry in the store's list. A gauge whose last sensor 40 year is before last year is inactive: Sumner closed on 1 April 2022 and was replaced by New Brighton Pier. The refresh makes 22 requests. `record_start` and `record_end`, the first and last sensor 40 years, are kept in the store's list so a backfill doesn't ask for years before them.
- **Not read:** Cape Roberts (`ROBT`) and Scott Base (`SCOT`), LINZ's two Antarctic gauges, have only sensor `00` files. Their formats change from year to year: five-minute rows with two field layouts and a Julian-day layout for Cape Roberts, a meter column before 2024 and millimeters after for Scott Base, whose README says its early times are NZST and gives none for the rest. They are left out until each file's clock and unit can be settled.
- **Files:** per gauge, year and sensor, `GET /api/listDatasetFiles/<CODE>/<year>/<sensor>` lists the zips under `/tidegauge/<CODE>/<year>/<sensor>/`: one per day, `WLGT_40_2026310.zip` for the 310th day of 2026, and, once the year is out, one for the year, `WLGT_40_2025.zip`, issued in early January. Each holds one CSV. A year's zip is about 2.3 MB, a day's about 7 KB. A year with a yearly zip is read from it alone; a year without one, from each day's file its range touches.
- **Rows:** a day's file has `WLGT,2026-11-06 00:00,2.549`, a year's `WLGT,20250410,00:00:00,02.629`. Levels are in meters above the sensor's tide gauge zero, times are UTC. A missing minute is `//.///` in a year's file or absent from a day's, and a value with a trailing `/` (`47.80/`, `02.22/`) is marked bad: the store drops both. A day's file holds `0.001` where a year's has the missing mark, so a sensor that was off reads as a level there, and the store drops a `0.001` from a day's file and a `0.000` from any file (erratum `linz-sensor-off-values`). A gauge whose tide crosses zero, such as Sumner, loses at most a minute a crossing. At Gisborne 52,020 minutes of 2025 are missing or marked, at Paratutae 4,584, at Puysegur Point 2,366.
- **Sensors:** every gauge but the two Antarctic ones has two, 40 and 41, each on a zero of its own. They agree to a few centimeters at first and then drift apart: the monthly median of sensor 40 minus sensor 41 stays within 0.03 m at Sumner from 2012 to 2016, and reaches 0.3 to 1.5 m, with a yearly cycle, at Lottin Point, Kaikoura, Korotiti Bay, Fishing Rock, Boat Cove and Napier. Neither is known to be the better one: against UHSLC's Wellington it is sensor 40 that swings by 0.4 m a year from 2015 to 2018 and sensor 41 from 2023 to 2024. The store reads sensor 40, so a series doesn't mix two zeros, except over the spans below where sensor 40 is stuck, erratic or missing and sensor 41 reads a tide whose level is within 0.25 m of sensor 40's healthy levels around it (the errata under Known limits, Sensor faults, list them). Sensor 41 is never offset to sensor 40, since the README gives no offset: the span's median level differs from sensor 40's healthy levels around it by 0.0 to 0.22 m (North Cape's first span, the largest), a step the rows don't mark, and the errata for each span name its station and days. This is the one place a series mixes two zeros.
- **Flags:** LINZ sends no quality flag and its READMEs say the data have not been quality controlled. A value from a day's file is `preliminary`, since the year's file replaces it, and a value from a year's file `good`, so a year LINZ never issued a yearly file for, such as Owenga's 2009 and 2010 or Sumner's 2021 and 2022, stays `preliminary` and a backfill without `--skip-written` fetches its daily files again; the store's QC applies to both. `finalizes` is true: the year's file corrects the daily files and Monthly's refetch fetches the year again from its earliest preliminary value.
- **Freshness:** daily files appear 6 to 12 days after the day, in batches. On 14 November 2026 Wellington's newest file was for the 6th, modified on the 12th, and each of its files from 19 October to 6 November was modified 6 to 12 days after its day. A request for the last 12 hours finds nothing, so the source isn't `hourly` and `live` is false. Nothing runs hourly: Monthly's refetch on the 9th brings new values. It reads every open station from two months back to the end of the month, then each from its earliest preliminary value, so a new year's first days and a new gauge are fetched too. Values reach the store up to six weeks after they're measured. The download page's own date, "Last updated Mon 19 Oct 2026", isn't a data date.
- **Same gauge elsewhere:** GESLA's 19 TTW records for these gauges, such as `gesla/wellington-wlgt-nzl-ttw`, are copies, and UHSLC's Wellington (`uhslc/071`), Gisborne (`078a`, `078b`), Napier (`668a`), Port Chalmers (`669a`) and Tauranga (`073a`) carry LINZ's contribution. Twelve gauges link by the existing rules, which need a shared name and a position within 2 km. The other seven GESLA records (Devonport, Owenga, Castlepoint, Paratutae, Puysegur Point, Boat Cove and Fishing Rock) are linked by decision in `LINKS`, since GESLA's file names carry LINZ's code but its names, or in three cases its longitude, differ: GESLA gives Boat Cove, Fishing Rock and Owenga east longitudes where the islands are west, 410 to 580 km off (erratum `gesla-ttw-longitudes`). Comparing 2019's UHSLC hourly values with LINZ's minute at the same instant, the series fit at lag 0, r 0.9991 at Wellington, 0.9967 at Napier, 0.9981 at Port Chalmers, 0.9995 at Tauranga and 0.9977 at Gisborne's `078b`. UHSLC's Auckland (`070a`, RNZN Hydrographic Office, 1984 to 1988, at 36.85°S 174.767°E) is 2.7 km from LINZ's Devonport gauge across the harbor and has no years in common with it, since Devonport starts in 2009, so nothing shows the two are one gauge and they aren't linked. Wellington's group prefers UHSLC's series (`PREFER`), since LINZ's own README sends long-term users to its reference gauge and neither of its sensors holds against it (erratum `linz-wellington-drift`).

## Datum

Levels are measured from each sensor's tide gauge zero (TG0), `ZERO`. The download page says LINZ has linked TG0 to a survey benchmark nearby "when feasible", and the READMEs state it two ways:

- **A calibration table** at 10 gauges (Owenga, Charleston, Castlepoint, Korotiti Bay, Kaikoura, Lottin Point, Paratutae, New Brighton Pier, North Cape, Welcombe Bay) lists the heights of its benchmarks and of chart datum (`CD`) above TG0 as of the calibration, such as `CD - 2.016 (LAT analysis)` at Owenga in 2011. The offset is for the zero of the sensors at the calibration date, so the store keeps it as `datums.CD` (the offset to add to a level in `ZERO`) only where the README lists no sensors replaced in that year or later: Castlepoint (−1.53 m, 2022), New Brighton Pier (−2.64 m, 2022) and North Cape (−2.66 m, 2023). At the other seven, a README lists sensors replaced after the calibration (Owenga in 2014 and 2019, Charleston in 2021, Korotiti Bay in 2023 and 2024, Kaikoura in 2018 and 2025, Lottin Point in 2025, Paratutae in 2021, Welcombe Bay in 2019), and `datums` is empty. The zero moves with the sensors: at Korotiti Bay, chart datum is 4.43 m above TG0 as of the 2021 calibration, and both sensors' levels step down about 0.8 m on 10 September 2024, when the sensors were replaced (errata `linz-korotiti-bay-sensors` and `linz-korotiti-bay-step-2024`). Only chart datum is kept, not the benchmarks. `chart_datum` isn't set from it.
- **A reference port** at 6 gauges (Devonport, Gisborne, Napier, Port Chalmers, Tauranga, Wellington) says "Chart Datum is 3.565m below BM ABPC" and to use "data from the above nearby reference gauge" for long-term analysis. It gives chart datum relative to a benchmark but not TG0's height relative to the benchmark, so it gives no offset and `datums` is empty. Wellington's `ZERO` readings run higher than UHSLC's Wellington by 1.2 to 2.4 m, with the zero stepping between, so a level here says nothing alone of chart datum.
- **Sumner** says "Chart Datum is 0.50m below TG0", so `datums.CD` is +0.5. **Boat Cove** and **Fishing Rock** give benchmark heights and "Tide gauge zero −6.002 m (nominal)" with no chart datum, so `datums` is empty.

`archive` is `previous`: each file is in the zero of its time. LINZ's READMEs list a sensor replacement or an earthquake and say nothing of the zero's height after most of them, so the store opens an epoch where the data shows a step, with a measured `to_current` where another record of the gauge gives one (Known limits).

## Known limits

LINZ warns that the sensors drift and advises caution for long-term analysis.

- **Sensor faults:** sensor 40 is stuck, erratic or missing for a spell at seven gauges, and where sensor 41 reads a tide the store reads sensor 41 for the spell (errata `linz-north-cape-both-sensors-stuck`, `linz-owenga-sensor-fault`, `linz-castlepoint-sensor-fault`, `linz-castlepoint-sensor-fault-2019`, `linz-north-cape-sensor-fault`, `linz-north-cape-sensor-fault-2013`, `linz-north-cape-sensor-fault-2014`, `linz-sumner-sensor-fault`, `linz-auckland-sensor-fault`, `linz-wellington-sensor-fault`, `linz-napier-sensor-fault`): Owenga from 25 November 2008 to 16 February 2010, Castlepoint from 29 January to 30 March 2012 and from 26 July 2019 to 25 July 2021, North Cape in four spells from July 2011 to January 2014, Sumner from 28 June 2016 to its closure, Devonport for eight days in 2012, and Wellington and Napier for a few weeks. Where both sensors are stuck, at North Cape from 22 September to 5 October 2011, neither is read. Where sensor 41 isn't within 0.25 m of sensor 40's healthy levels, the spell is flagged `suspect` and sensor 40 is kept: Devonport's from 11 July to 27 August 2012, Boat Cove's in 2013 and 2014, Fishing Rock's from December 2016 to March 2017 and Napier's in December 2010 (errata `linz-devonport-sensor-fault-2012`, `linz-boat-cove-sensor-fault-2013`, `linz-boat-cove-sensor-fault-2014`, `linz-fishing-rock-sensor-fault`, `linz-napier-sensor-fault-2010-12`). Korotiti Bay's two sensors disagree by up to 1.2 m from August 2021 to September 2024, and that span is flagged `suspect` too (erratum `linz-korotiti-bay-sensors`). QC's flatline rule flags any sensor held at one level. The spans were found from the daily range and median of both sensors in every yearly file of the 19 gauges. Years LINZ serves only as daily files weren't examined for faults: 2026, and a few earlier ones such as Owenga's 2009 and 2010 sensor 40 and Sumner's 2021 and 2022. Where a span reads sensor 41 through such years it was checked another way, against sensor 40 after the replacement at Owenga and against UHSLC's Lyttelton on every seventh day at Sumner. A fault after 2025 has no span until one is added in `SENSOR_41` in [index.ts](index.ts). Sensor 41 has failures of its own, which the READMEs list for Owenga (2013), Castlepoint (2021) and North Cape (2015); where a span reads it through one, QC judges the values, as for Owenga's spikes of 11 February 2010 and Castlepoint's 26 July 2021.
- **Kaikoura's earthquake:** the gauge and its benchmark were lifted 0.88 m on 14 November 2016 NZDT (13 November, 11:02 UTC), which the README says (erratum `linz-kaikoura-uplift`). Its daily means fall from about 3.4 m on 12 November to 2.4 m on 14 November. The 13th is flagged `suspect` and a datum epoch starts on the 14th. The epoch before it converts to the later one by the README's 0.88 m (`overrides.epochs`). Values from 11:02 UTC on the 13th are on the new zero but stored in the earlier epoch, which is why the whole day is flagged.
- **Wellington's drift:** against UHSLC's hourly Wellington, sensor 40's monthly median offset swings between 1.94 and 2.37 m from June 2015 to February 2018 while sensor 41 holds 2.03 to 2.07 m, and in 2023 and 2024 sensor 41 swings from 1.16 to 1.82 m while sensor 40 stays within 1.33 and 1.56 m. The zero also steps down, which the epochs record (below). Nothing is flagged, since neither sensor holds throughout, and UHSLC's series is preferred (erratum `linz-wellington-drift`).
- **Steps in the zero:** a gauge's levels are above its sensors' own zero, which moves when sensors are replaced or calibrated, by amounts the READMEs rarely give. Against UHSLC's hourly records both sensors step together at Wellington (−0.26 m on 30 May 2012 and −0.38 m on 15 April 2021, which the README doesn't list), Port Chalmers (−0.56 m on 26 May 2021), Tauranga (−0.47 m on 20 March 2024, not listed) and Napier (−0.34 m in 2008) and Gisborne (−0.57 m on 26 September 2013, −0.41 m on 12 May 2021 and −0.54 m on 13 December 2024, none listed). Each is a datum epoch with the measured step as its `to_current` (errata `linz-wellington-step-2012`, `linz-wellington-step-2021`, `linz-port-chalmers-step-2021`, `linz-tauranga-step-2024`, `linz-napier-step-2008`, `linz-gisborne-step-2013`, `linz-gisborne-step-2021`, `linz-gisborne-step-2024`), good to the 0.01 to 0.08 m the offsets scatter by over 30 days. Korotiti Bay's step on 10 September 2024 has no record to measure against, so its earlier epoch has no `to_current`. At Wellington in March 2018, Napier in April 2018 and Tauranga in June 2020, when the README lists sensors replaced, sensor 40 alone steps (−0.51, −0.56 and −0.28 m), which is the replacement resetting its drift, not the zero, so those stay. Only these five gauges have a UHSLC copy, so another gauge's steps are unknown and its levels are as LINZ serves them (erratum `linz-zero-steps`).
- **High values at New Brighton Pier:** four days of its 2025 file read 13.4 to 13.9 m, 1,440 minutes each from 23:54 UTC on 8 February, 19 May, 27 August and 5 December, 5,760 in all, at a gauge whose other minutes run from 2.9 to 5.6 m. QC flags every one `suspect`, which the stored 2025 file shows (erratum `linz-new-brighton-pier-high-values`). Sensor 41 there reads 11.7 to 12.2 m from August 2024 and isn't used.
- **Napier's step:** the README notes "step in data on February 25" of 2008. The data step down 0.344 m at 18:51 UTC on 24 February, after a gap, by both sensors against UHSLC's Napier. The levels before it convert to the later zero in an earlier epoch, and the five hours of 24 February after the step are left out, since epochs start on a whole day (erratum `linz-napier-step-2008`).
- **Sensor changes:** READMEs list replacements and maintenance by year: 2012, 2018 and 2023 at Devonport, 2019 and 2021 at Charleston, 2024 at Gisborne and Korotiti Bay, 2025 at Kaikoura and Lottin Point, and others. Most state no change of zero, and the steps found against UHSLC are above. Nothing else is flagged for them.
- **Scott Base's shifts:** Scott Base's README lists shifts of TG0 by date, such as 0.122 m up on 18 January 2019 and 0.130 m down on 17 February 2021, and says data from 8 February to 17 March 2021 are unreliable. Scott Base isn't read (see above), so none of them reach the store.

## Running ingest

- **Limits:** LINZ publishes no rate limit, and its files come through a CDN. Requests start a second apart. The listings and READMEs are never cached; a year's zip is cached once its year began four years ago, since LINZ issued 2019's in January 2022, and a daily file is rewritten without notice. A past year in a gauge's record whose listing is empty fails the request rather than read as a year with no data. Every gauge's sensor 40 years run without a gap, and LINZ lists a file for each day of Sumner's 2021 and 2022 whatever sensor 40 holds in them, so an empty past year is a bad answer. Backfill replaces each month it fetches, so the year's file replaces a month's daily values, those it marks missing included. A listing can't be checked for completeness, since LINZ lacks days at times (Gisborne's 2026 listing has 299 of 310 days), so a month whose listing omits a day and holds others replaces the stored values for the omitted day.

### Backfill

Monthly refreshes the list on the 2nd, like the other sources. Dispatch Monthly with `sources: linz` once the adapter is on `main`, since Compact daily and the refetch skip LINZ until its list is in the store. Then, through the Ingest workflow, Sumner's closed record needs `--with-inactive`:

```bash
node scripts/ingest.ts backfill linz all 2007 2026 --skip-written --with-inactive
node scripts/ingest.ts backfill linz all 2026 2027 --shard 1/3
```

That's 306 past station-years, one listing and one 2.3 MB zip each, about 700 MB and 10 minutes of requests at a second apart. The current year is 19 gauges of up to 313 daily files each, about 5,900 requests, so about 1.7 hours, split in shards that each fit in a run: `--shard 2/3` and `3/3` follow. A gauge with no file for a year, such as one that began in June, asks for the listing and writes nothing for it. From then on, Monthly's refetch on the 9th fetches the current year's daily files again, about the same 1.7 hours in the year's last months, and the year's file once it's out.

A store that already holds LINZ's years from sensor 40 alone keeps the stuck and erratic values in the spans of `SENSOR_41`, since `--skip-written` skips every ended year and `mergeFetched` replaces only the months a run fetches. Dispatch Monthly with `sources: linz` and `accept_epochs` checked first, since the splits open nine datum epochs, more than a refresh accepts on its own, and run these straight after, since until they finish the API returns nothing for these six stations from their first split day on. Then fetch the stations' span years again, and requalify the flagged spans of Korotiti Bay, Boat Cove and Fishing Rock (Devonport and Napier's are written by their refetch):

```bash
node scripts/ingest.ts backfill linz SUMT 2016 2023 --refetch
node scripts/ingest.ts backfill linz CHIT 2008 2011 --refetch
node scripts/ingest.ts backfill linz CPIT 2012 2013 --refetch
node scripts/ingest.ts backfill linz CPIT 2019 2022 --refetch
node scripts/ingest.ts backfill linz NCPT 2011 2015 --refetch
node scripts/ingest.ts backfill linz AUCT 2012 2013 --refetch
node scripts/ingest.ts backfill linz WLGT 2012 2027 --refetch
node scripts/ingest.ts backfill linz OTAT 2021 2027 --refetch
node scripts/ingest.ts backfill linz TAUT 2024 2027 --refetch
node scripts/ingest.ts backfill linz GBIT 2024 2027 --refetch
node scripts/ingest.ts backfill linz NAPT 2007 2027 --refetch
node scripts/ingest.ts backfill linz GIST 2013 2027 --refetch
node scripts/ingest.ts requalify linz GBIT 2021 2025
node scripts/ingest.ts requalify linz RBCT 2013 2015
node scripts/ingest.ts requalify linz RFRT 2016 2018
```

That's 80 station-years, each one listing and a 2.3 MB zip for each sensor read, and for Owenga's 2009 and 2010, Sumner's 2021 and 2022 and every station's 2026 a request per day. Each split's epochs are written by the refetch from its first day, since values already stored from that day on lie in the earlier epoch's files, outside its span.
