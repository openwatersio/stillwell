# NOAA CO-OPS (`coops`)

Observed water levels and verified high and low waters for the US National Water Level Observation Network and the historical stations before it, from the [metadata API](https://api.tidesandcurrents.noaa.gov/mdapi/prod/) and the [data API](https://api.tidesandcurrents.noaa.gov/api/prod/).

- **License:** U.S. Government work, public domain. Attribution "NOAA National Ocean Service, CO-OPS" is carried. Requests send `application=openwaters`, as CO-OPS asks.
- **Contact for errors:** Tide.Predictions@noaa.gov, the Stakeholder Services Branch, which [CO-OPS's contact page](https://tidesandcurrents.noaa.gov/contact.html) names for oceanographic data requests. CO-OPS publishes no channel for data errors as such.
- **Stations:** the historical water-level list (`type=historicwl`, 2,930 stations, which includes nearly all current ones) and the current network (`type=waterlevels`, 303). The oldest station's record starts in 1897, and 2,825 are in the US, 54 in Puerto Rico and 14 in the US Virgin Islands. Every listed station is `active`, since CO-OPS still lists it; only current-network stations are `live`, and only they have `interval_s` (360), since a historical station may have only hourly heights. An empty current list fails the refresh rather than taking every station off the live feed. Great Lakes stations (`greatlakes`, or `tideType` "Great Lakes", which alone marks Point Aux Frenes, 9075199) are `lake`, other tidal stations `coastal`. The 43 stations CO-OPS marks neither tidal nor Great Lakes, most of them removed long ago (sounds, canals and lagoons in North Carolina, Florida, Louisiana, Texas and Alaska, and six in Puerto Rico), are null. `country_code` comes from CO-OPS's `state`, which holds a US state, a code that is its own country code (PR, VI, GU, AS, MP, FM, MH, PW, UM), or a country's name; anything else is null.
- **Datum:** every level is in station datum (STND), the gauge's own fixed zero, not MLLW. MLLW, like every tidal datum, is recomputed against the gauge for each National Tidal Datum Epoch, so a series in MLLW would change datum when the next epoch is adopted. `datums` (about 2,300 stations have them, 631 none) gives each published datum from STND (MHHW, MHW, DTL, MTL, MSL, MLW, MLLW, NAVD88, NGVD29, LAT, HAT, and LWD on the Great Lakes), so `level_m + datums.MLLW` is the level above MLLW. They're fetched fresh on every refresh, so a new epoch's values arrive. The span CO-OPS reduced them over (`DatumAnalysisPeriod`, from the earliest date it gives to the latest) is kept as `datums_period` and published as each tidal datum's `datums_epoch`; a refresh that gets no datums keeps the offsets and the span it had. On the Great Lakes STND is IGLD 1985, checked against the data API at Algonac, Buffalo, Calumet Harbor, Duluth and Oswego, so `datums.IGLD` is 0 at stations CO-OPS marks `greatlakes`; Point Aux Frenes, marked only by `tideType`, hasn't been checked and gets no `IGLD`.
- **Levels:** the 6-minute `water_level` product, a calendar month per request (the API allows 31 days). The 6-minute record starts between 1994 and 1996, depending on the station. Before 1997, where a month's 6-minute record starts late or not at all, `hourly_height` fills in the part before it. From 1997 on, a month without 6-minute values is a gap, not the hourly era, so it isn't filled with hourly heights. `q` is `v` once CO-OPS verifies a value and `p` while it's preliminary. For 6-minute values the flat (F) and rate-of-change (R) flags make a value suspect, and so does the limit flag (L) unless CO-OPS has verified the value (`q` is `v`): on verified values L is left from CO-OPS's acquisition check against expected limits that are stale at some stations (erratum `coops-stale-limit-flag`). The outlier flag (O) counts rejected one-second samples, so it doesn't. Hourly heights are verified too, and their L marks ordinary values the same way, on whole records at some stations, so it doesn't make them suspect either; inferred (I) is `interpolated`. The store keeps the flag, not CO-OPS's letters, so years written before this rule keep verified 6-minute and hourly L values as `suspect` until a backfill with `--refetch` reads them again. As with USGS's qualifiers, a preliminary value CO-OPS flags is stored with `suspect` as its source flag, so the Monthly refetch, which starts from a station's earliest preliminary value, doesn't come back for it; its verified value arrives only through a `--refetch`.
- **Extremes:** the verified `high_low` product, a calendar year per request, at tidal stations. CO-OPS refuses a request over 365 days, so a leap year goes in two halves split at July 1. Higher high and lower low waters are kept as `high` and `low`. Their limit flag (L) still makes them suspect.
- **Not fetched:** CO-OPS's predictions, since Slackwater computes its own; and months outside a station's established and removed dates, so a backfill doesn't ask for decades a station wasn't there. The station list's details give those dates, and the source's list in the store keeps them as `established` and `removed` (they aren't in `stations.parquet`). A station removed before it was established was reinstalled, and a live station is running whatever its removed date says, so neither skips anything; a station the list gave no dates for has them looked up in its details; a date that doesn't parse fails the backfill rather than skipping every year.
- **Rate limit:** the metadata API blocks a client for a few minutes once it passes a rate limit, answering 403 ForbiddenException from its AWS gateway. Its requests start at least a second apart, and a 403 waits two and a half minutes, then five, before giving up, so a station refresh takes about 50 minutes (one datums request per station). A station whose datums still fail keeps the ones it had; five failures in a row, more than a tenth of stations, or two hours in all fail the refresh at once, and the store's list stays as it was. The data API blocks the same way: a backfill asking for four stations' months at once, with no pause, was refused after about 16 seconds. So data requests start at least a second apart (`pacing.dataMs`), and a 403 holds every data request for two and a half minutes, the next for five. Only answers that went over the network after the current hold began count: a 403 for a request already in flight is the same block, and a cached answer is no sign it has lifted. Only a request's first try starts a hold, and its retries fail that request alone, so a URL CO-OPS refuses on its own costs one hold. A third hold in a row, from three requests refused in turn, throws `Blocked` (from [`src/http.ts`](../../http.ts)): every data request after it fails at once without going out, and backfill stops instead of going on through its stations. That takes 7.5 minutes and at least three requests. Three URLs refused one after another with nothing answered between them look the same as a block and stop the run too; the next run picks up where it stopped. A metadata 403 fails only its request, as above, and the station refresh has its own limits. The two APIs are paced separately, so a backfill looking up details can send up to two requests a second to the host, and runs that overlap, such as shards running at once, each pace themselves as if alone and have to split the rate between them. At a second a request, a backfill from 1996 on is about 210,000 requests (a month of 6-minute levels for each month between a station's established and removed dates, plus a `high_low` request per year at the non-lake stations, two in a leap year), about 58 hours, ten or more of the Ingest workflow's runs with `--skip-written` and `timeout` at 360 (its default is 180 minutes). Years a station returns nothing for write no file. A `--skip-written` campaign records them and skips them for 30 days; without that, each run would ask again for every empty year inside a station's dates before reaching new stations, as at Alameda (9414750), dated from 1939 with nothing served before 1985, at about 25 seconds a year. Ingest hourly reads the last 12 hours at the 303 live stations, and its sweep takes about 5 minutes; a block there fails the stations after it, which keep what they had, and fails the run.
- **Months:** a backfill asks for a year as 12 monthly requests, and a month CO-OPS answers with "No data" leaves that month's stored values alone; the store only replaces a month a fetch returned values for.
- **Freshness:** data responses whose range ends within the last 120 days, error answers (which CO-OPS sends with HTTP 200), and all station metadata, are never cached, since CO-OPS replaces preliminary values as it verifies them and updates datums with each epoch. On the 9th the Monthly workflow refetches each station from its earliest preliminary value, from January three years back on, so verified values replace preliminary ones.
