# NOAA CO-OPS (`coops`)

Observed water levels and verified high and low waters for the US National Water Level Observation Network and the historical stations before it, from the [metadata API](https://api.tidesandcurrents.noaa.gov/mdapi/prod/) and the [data API](https://api.tidesandcurrents.noaa.gov/api/prod/).

- **License:** U.S. Government work, public domain. Attribution "NOAA National Ocean Service, CO-OPS" is carried. Requests send `application=openwaters`, as CO-OPS asks.
- **Stations:** the historical water-level list (`type=historicwl`, about 2,900 stations, which includes nearly all current ones) and the current network (`type=waterlevels`, about 300). Every listed station is `active`, since CO-OPS still lists it; only current-network stations are `live`, and only they have `interval_s` (360), since a historical station may have only hourly heights. An empty current list fails the refresh rather than taking every station off the live feed. Great Lakes stations are `lake`, other tidal stations `coastal`. `country_code` comes from CO-OPS's `state`, which holds a US state, a code that is its own country code (PR, VI, GU, AS, MP, FM, MH, PW, UM), or a country's name; anything else is null.
- **Datum:** every level is in station datum (STND), the gauge's own fixed zero, not MLLW. MLLW, like every tidal datum, is recomputed against the gauge for each National Tidal Datum Epoch, so a series in MLLW would change datum when the next epoch is adopted. `datums` gives each published datum from STND (MHHW, MHW, DTL, MTL, MSL, MLW, MLLW, NAVD88, NGVD29, LAT, HAT, and LWD on the Great Lakes), so `level_m + datums.MLLW` is the level above MLLW. They're fetched fresh on every refresh, so a new epoch's values arrive. On the Great Lakes STND is IGLD 1985, checked against the data API at Algonac, Buffalo, Calumet Harbor, Duluth and Oswego, so `datums.IGLD` is 0 there.
- **Levels:** the 6-minute `water_level` product, a calendar month per request (the API allows 31 days). Before 1997, where a month's 6-minute record starts late or not at all, `hourly_height` fills in the part before it. From 1997 on, a month without 6-minute values is a gap, not the hourly era, so it isn't filled with hourly heights. `q` is `v` once CO-OPS verifies a value and `p` while it's preliminary. For 6-minute values the flat (F), rate-of-change (R) and limit (L) flags make a value suspect; the outlier flag (O) counts rejected one-second samples, so it doesn't. For hourly heights, inferred (I) is `interpolated` and limit (L) is suspect.
- **Extremes:** the verified `high_low` product, a year per request, at tidal stations. Higher high and lower low waters are kept as `high` and `low`.
- **Not fetched:** CO-OPS's predictions, since Slackwater computes its own; and months outside a station's established and removed dates, so a backfill doesn't ask for decades a station wasn't there. The station list's details give those dates, and the source's list in the lake keeps them as `established` and `removed` (they aren't in `stations.parquet`). A station removed before it was established was reinstalled, and a live station is running whatever its removed date says, so neither skips anything; a station the list gave no dates for has them looked up in its details; a date that doesn't parse fails the backfill rather than skipping every year.
- **Rate limit:** the metadata API blocks a client for a few minutes once it passes a rate limit, answering 403 ForbiddenException from its AWS gateway. Its requests start at least a second apart, and a 403 waits two and a half minutes, then five, before giving up, so a station refresh takes about 50 minutes (one datums request per station). A station whose datums still fail keeps the ones it had; five failures in a row, more than a tenth of stations, or two hours in all fail the refresh at once, and the lake's list stays as it was. The data API blocks the same way: a backfill asking for four stations' months at once, with no pause, was refused after about 16 seconds. So data requests start at least a second apart (`pacing.dataMs`), and a 403 holds every data request for two and a half minutes, the next for five. Only answers that went over the network after the current hold began count: a 403 for a request already in flight is the same block, and a cached answer is no sign it has lifted. Only a request's first try starts a hold, and its retries fail that request alone, so a URL CO-OPS refuses on its own costs one hold. A third hold in a row, from three requests refused in turn, throws `Blocked` (from `src/http.ts`): every data request after it fails at once without going out, and backfill stops instead of going on through its stations. That takes 7.5 minutes and at least three requests. Three URLs refused one after another with nothing answered between them look the same as a block and stop the run too; the next run picks up where it stopped. A metadata 403 fails only its request, as above, and the station refresh has its own limits. The two APIs are paced separately, so a backfill looking up details can send up to two requests a second to the host, and runs that overlap, such as a `stations` refresh beside a backfill or shards running at once, each pace themselves as if alone and have to split the rate between them. At a second a request, the backfill's roughly 100,000 requests (monthly 6-minute and hourly levels, plus a `high_low` request per year) take about 28 hours, five or more of the Ingest workflow's runs with `--skip-written` and `timeout` at 360 (its default is 180 minutes). Years a station returns nothing for write no file, so each later run asks for them again before reaching new stations. The hourly `recent` sweep's 302 requests take about 5 minutes; a block there fails the stations after it, which keep what they had, and fails the run.
- **Months:** a backfill asks for a year as 12 monthly requests, and a month CO-OPS answers with "No data" leaves that month's stored values alone; the lake only replaces a month a fetch returned values for.
- **Freshness:** data responses whose range ends within the last 120 days, error answers (which CO-OPS sends with HTTP 200), and all station metadata, are never cached, since CO-OPS replaces preliminary values as it verifies them and updates datums with each epoch. The Monthly workflow refetches last year and this year up to the current month on the 9th, so verified values replace preliminary ones.
