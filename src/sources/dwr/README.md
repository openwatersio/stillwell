# California Department of Water Resources (`dwr`)

Stage every 15 minutes at 50 tidal gauges in the Sacramento–San Joaquin Delta and Suisun Marsh, back to 1975 at the oldest, from the [Water Data Library](https://wdl.water.ca.gov/ContinuousData.aspx) (WDL), DWR's continuous monitoring data. The [CNRA open data portal](https://data.cnra.ca.gov/dataset/fcba3a88-a359-4a71-a58c-6b0ff8fdc53f) lists WDL's stations (`stations.csv`) and a download link for each station and parameter (`station-trace-download-links.csv`). Each link is a CSV on Azure blob storage with the station's whole record, which DWR rewrites daily.

- **License:** WDL states no license. DWR's [Conditions of Use](https://water.ca.gov/Conditions-of-Use) are a privacy notice and a disclaimer: DWR "does not guarantee the accuracy, completeness, timeliness, or correct sequencing of the information". The CNRA portal gives the dataset's license as "not specified". Nothing restricts redistribution or commercial use, so `redistribution` and `commercial_use` are true, and every station is in the public lake, credited to the "California Department of Water Resources". `terms` carries the disclaimer.
- **Contact for errors:** wdlweb@water.ca.gov, which the [Water Data Library's contact page](https://wdl.water.ca.gov/ContactUs.aspx) gives for questions about the data or the site.
- **Stations:** the DWR records TICON keeps (`cdwr`) that WDL has a raw level file for, `dwr/<DWR station number>` (`dwr/B95050Q` for Fisherman's Cut), all `estuary`. The list is kept in the adapter (`TIDAL`). TICON's records carry the DWR number without the trailing Q of the NAVD88 stations, so the TICON inventory matches them by number, adding the Q where `TIDAL` has it. TICON names its other California records by CDEC code (BDL, MRZ, HOL and so on); those are CDEC stations, not in WDL, not read here, and come from `cdec` instead. In November 2026, 71 of TICON's stations have a level file listed, and 50 are taken: WDL lists no position for five closed ones (Hood, Old River near Rock Slough, Benicia, Mallard Island, Montezuma Slough at Roaring River), 15 files are empty, and the file for San Joaquin River at Venice Island (B95580) carries another station's header (B95500's, with no notes). So a refresh probes each file's first KB, leaves out a file that's empty, has no data row or names another station (B95580 was listed before this check, so the lake keeps it as an inactive station with no data), for a new station falls back from an unusable NAVD88 file to its stage file, and leaves out a station with no file that has data. A trace row with no times, or a station with no name, is left out too. Positions are as the station list gives them, in NAD83 or WGS84 at most stations; a few closed ones, such as Collinsville (B91110), are in NAD27, about 100 m off, and aren't converted. A station silent for a year is `inactive`; five are. None is `live`, since the files run a day or more behind.
- **Parameters:** `WaterSurfaceElevationNAVD88`, "Water Surface Elevation (NAVD88) (feet)", in `NAVD88`, where a station has it (16), and otherwise `StreamLevel`, "Corrected Stage (Feet)", above the gauge's own zero, `GZ` (34). The stage files don't name the gauge zero's datum, so `datums` is empty. Only the raw point series (`RAW`) is read; daily means are left out. A file whose notes name another variable is refused: a whole file from its notes, and a tail read from the file's first KB, checked once per process.
- **Levels:** feet, as meters, every 15 minutes on the quarter hour. Rows are `MM/DD/YYYY HH:MM:SS, value, quality,`, with notes beside the first rows in a fourth column naming the station, the variable and the quality codes. A missing reading has an empty value.
- **Requests:** a range from two years back or older reads the whole file, 0.5 to 65 MB, about 2 GB for all 50, and keeps the four most recent files in memory for the process, so a backfill at the default `--concurrency` of 4, which asks for a station a year at a time, mostly downloads each file once for its older years. A file can still be evicted while its station waits on a write, and a higher concurrency evicts files still in use, so some are downloaded again. Each file held is up to about 1.5 million readings in memory. A more recent range, such as the monthly refetch, reads the file's tail with a byte range. Azure doesn't serve a range counted from the end, so the offset is a guess from the record's start: rows are 43 bytes with a value and 33 without, so guesses at 43, 41 and 33 bytes a row go in turn, and the whole file is read if none reaches back far enough. Tail reads aren't kept, so a backfill reads the tail again for each of the last two years. A guess past the end gets a 416 and costs nothing.
- **Flags:** Hydstra's quality codes, which each file lists: 1 (good), 2 (good, edited) and 40 (fair measurement) are `good`; 70 (estimated) and 76 (reliable interpolation) are `interpolated`; 151 (missing) and 255 (no data) are dropped; 170 (unreliable) and any other code are `suspect`. WDL marks nothing as provisional, but DWR edits its data after publishing it, and its stage files arrive months after the readings, so values from the current calendar month and the three before it are at most `preliminary`. That makes `finalizes` true.
- **Times:** Pacific Standard Time all year. Against NOAA's Port Chicago (9415144), Fisherman's Cut lags 170 minutes in January and in July 2026 (r 0.96 and 0.97). CDEC's real-time stage at the same gauge (FCT) reads 0.13 ft lower and, in July, an hour later on the clock, so CDEC keeps daylight saving although its pages say PST.
- **Datum:** NAVD88 or the gauge's zero, by parameter. A new station takes NAVD88 where its file has data; a listed station keeps its parameter, so an empty file at refresh time leaves it out for the month rather than move it to another datum. The stage files don't say whether a gauge's zero was ever reset, so a reset in a long stage record would show only as a step. `archive` isn't set.
- **Freshness:** WDL rewrites the files daily, and they end a day or two before the request: on 7 November 2026, Fisherman's Cut ended at 10:45 PST on 5 November, and the stage files months back. So `hourly` is false, and new values arrive through Monthly's refetch on the 9th, which for DWR reads every active station again from January of last year to that day, finished years included (`--refetch`), rather than only the stations that hold a preliminary value: the generic refetch never reads past the end of a station's last stored year, and drops a station once it holds no preliminary value. That's two tail reads a station, about 100 MB a month. Values a stage file gains more than a year after their time aren't fetched again without a manual backfill. Files are in time order; one that isn't is sorted, and a repeated time keeps its last row.
- **Not USGS or NOAA:** WDL's data is DWR's own: every station in `TIDAL` is `source` "DWR Hydstra" in the station list, and a station from any other source is left out.
- **Limits:** none published. Nothing is cached on disk, since DWR rewrites every file daily.

## Backfill

Monthly refreshes DWR's list on the 2nd. Dispatch Monthly with `sources: dwr` once the adapter is on `main`, then backfill through the Ingest workflow, active stations first and the five inactive ones in a second run:

```bash
node scripts/ingest.ts backfill dwr all 1975 2026 --skip-written
```

```bash
node scripts/ingest.ts backfill dwr B91110,B91210,B95400,B95480,E33510 1975 2026 --skip-written
```

That's about 1,400 station-years, but each station's file is downloaded once, about 2 GB in all, which should fit in one Ingest run. The current year is fetched whole on every run, so backfill it on its own with `backfill dwr all 2026 2027`. From then on, Monthly's refetch on the 9th reads each active station's last year or two again from the tail of its file.
